Device Bound Session Credentials (DBSC) and Phishing

Device Bound Session Credentials help protect users after sign-in by making stolen cookies harder to replay. That is a strong improvement. It does not mean live Adversary-in-the-Middle phishing is solved.

Quick answer

Does DBSC stop phishing?

DBSC helps stop stolen cookie replay. It does not stop every phishing attack, especially live AiTM attacks where the victim's real browser remains active in the session path.

What DBSC protects

DBSC binds session continuity to the original device, reducing the value of cookies stolen by infostealers, XSS, leaked logs, or exposed headers.

What DBSC does not solve

DBSC does not decide whether a login page is legitimate. It does not stop a user from interacting with a live phishing proxy.

What still matters

Strict phishing-resistant MFA enforcement, context-aware access, browser protections, and realistic testing still matter for live AiTM risk.

What Are Device Bound Session Credentials?

Device Bound Session Credentials, or DBSC, are a browser and web-platform mechanism that lets a site bind a session to a cryptographic key held by the user's browser. Chrome can store that private key in protected hardware, such as a Trusted Platform Module on Windows or Secure Enclave on macOS. The site can then require proof that the same browser still has the key before refreshing short-lived session cookies.

That makes stolen cookies less portable. If malware steals a session cookie and sends it to an attacker, the attacker should not be able to keep refreshing the session from another machine without the bound key.

Does DBSC Stop Session Hijacking?

It depends what kind of session hijacking you mean. DBSC is excellent for reducing stolen cookie replay. It is much less direct against live Adversary-in-the-Middle (AiTM) phishing, where the victim's own browser remains connected and participates in the session.

In a live AiTM attack, the attacker is not only replaying an old cookie from a new device. The proxy relays traffic while the user signs in. The device-bound browser is still present. That is why DBSC should be treated as a cookie-theft defense, not a complete phishing defense.

How Should Defenders Use DBSC?

Defenders should enable and monitor DBSC where it is available. They should also avoid overclaiming it internally. The best message is simple: DBSC makes stolen sessions harder to reuse, but it does not remove the need for phishing-resistant authentication enforcement and realistic phishing tests.

For live AiTM phishing, the stronger control is server-side enforcement of phishing-resistant authentication. If the identity provider allows fallback to a phishable factor, a live proxy can still route the user toward the weaker path. If policy requires a phishing-resistant method for the protected app, the attack fails cleanly.

Best defensive stack

  • DBSC for stolen-cookie replay
  • Passkeys or hardware keys for phishing-resistant auth
  • Authentication-strength enforcement to prevent fallback
  • Context-aware access for device and session policy
  • Realistic phishing assessment to validate the full path
