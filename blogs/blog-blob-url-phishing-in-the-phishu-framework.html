The Sign-In Page That Was Never on a Server: Blob URL Phishing in the PhishU Framework

A phishing page that is assembled inside the victim's own browser never exists at an address anything else can fetch. The PhishU Framework now reproduces the technique as a toggle on any standard Landing Page, and the most useful part is what it lets you measure.

Most phishing defenses share an assumption that sounds too obvious to question: if there is a malicious page, it lives somewhere and something can go look at it. Follow the link, fetch what comes back, judge it, blocklist the address so the next person is protected.

Barracuda published research on September 9 describing a campaign that breaks that assumption, and the security press picked it up within days. The sign-in page is never fetched from anywhere. It is built inside the victim's browser by a few lines of JavaScript and opened from a temporary address the browser invents on the spot. It exists in exactly one tab, and it disappears when that tab closes.

The campaign Ashitosh Deshnur and his team documented used a document-signing lure carrying a calendar invitation, routed through a Microsoft sign-in endpoint and on into Microsoft Teams, which loaded an outside resource that did the assembling. Every hop a filter could inspect early looked like normal Microsoft traffic. Barracuda frames it as a direction of travel rather than one campaign, which is why we built it into the Framework the same week rather than waiting for it to turn up in an engagement.

The short version: A blob: URL is an address a browser generates for a chunk of data it is holding in memory. Nothing outside that one tab can fetch it, it is different for every visitor, and it dies with the tab. Build a sign-in page that way and there is no page on a server to retrieve, analyze, or blocklist. The PhishU Framework now ships this as a per-Landing-Page toggle, so authorized engagements can test whether a target notices the one thing that does give it away.

What a Blob URL Actually Is

This is a normal web feature, not an exploit. Browsers let JavaScript hold a chunk of data in memory and ask for a temporary local address to refer to it. That is how a web app lets you preview an image before uploading it, or generate a file for download without a round trip to a server.

The address comes back looking like this, with the site's own origin followed by a random identifier:

blob:https://signin.example-portal.com/6b41f0a2-9d3c-4e77-a1b8-5f2c0e9d7a34

Point a browser at that address and it renders whatever was in memory. If that happens to be a complete HTML sign-in page, you get a complete HTML sign-in page. It looks and behaves like any other, because it is one. It simply never travelled over the network.

The consequences follow from that. Nothing outside the tab can request the address. Two people visiting the same lure get two different identifiers. Close the tab and it stops meaning anything. There is no durable thing to add to a feed, share with a partner, or check tomorrow.

Researchers classify the underlying method as HTML smuggling, tracked by MITRE as T1027.006. The usual form smuggles a file into the browser to get past attachment scanning. This form smuggles the page.

Three Things That Get Confused

Coverage of browser-based phishing runs several different techniques together, and the names are similar enough that it is worth separating them.

Technique What actually happens
Browser-in-the-Browser A fake browser window is drawn inside the real page, complete with a painted address bar showing whatever the attacker wants. Nothing is faked at the network level. The trick is entirely visual.
Browser-in-the-Middle The victim is remotely operating a real browser running on attacker infrastructure, streamed to their screen. They sign in to the genuine site, but the session lives on the attacker's machine.
Blob URL phishing The page is assembled in the victim's own browser and opened from a temporary blob: address. About how the page is delivered and rendered, not about whose browser is involved.

They are compatible rather than competing. A blob-rendered page can carry a Browser-in-the-Browser overlay inside it, because once the page is rendered it is an ordinary page.

Reproducing It in the PhishU Framework

The Framework already had the two hard parts: a Landing Page pipeline that assembles the page content before serving it, and a runtime that decides what a given visitor is allowed to see. Adding blob rendering meant changing the last step of delivery, not building a new kind of page.

The result is a switch on the Landing Page Behaviors tab. Turn it on and the page an operator already designed gets delivered the new way. No re-authoring, no separate template, no duplicate content to maintain.

Two constraints shaped it. The blocking controls had to keep working exactly as before, so blocklists, auto-block, and the checks that keep scanners away all still run before the page is assembled and a blocked visitor never reaches the new path. Credential capture, tracking, and reporting had to survive the move, since a technique that breaks attribution produces a campaign you cannot report on.

The toggle is deliberately unavailable where it would make no sense. A proxy-based page relays a live session from a real provider, so there is no assembled document to build. Consent and device-code pages hand the target off to a real provider flow that a blob navigation would disrupt. Those are filtered out rather than left as a way to break a campaign.

Being Precise About What This Adds

The headline version of this story is stronger than the truth, so two limits are worth stating plainly.

A security product that fully renders a page, runs its JavaScript, and inspects the result will see a blob-rendered sign-in page. It gets built in that sandbox's browser the same way it would in a victim's. Anyone calling this invisible to security tooling is describing filters that fetch and read, not filters that render and watch.

The link is the other limit. The email still carries an ordinary address that belongs to the operator, still resolves, and can still be blocked like any other. What has no durable address is the credential page at the end. The in-the-wild campaign laundered its early hops through legitimate cloud services to make the visible link look trustworthy, which the Framework does not reproduce, because it rests on third-party redirect behavior that can be fixed at any time.

So what is genuinely new: the credential page no longer has an address at all, which removes the durable artifact that blocklisting and threat-feed sharing depend on. It is the technique attackers are actually using, run the way they run it. And it produces an unusually clean test of whether a target notices, which is the part with the most value to a defender.

The One Thing a Target Can Actually See

Every phishing technique worth testing has a tell, and most are subtle. A lookalike domain needs the reader to know what the real one was. A display-name spoof needs them to expand the header. Those are hard to teach because the signal is a judgment call.

This one is not, which is what makes it good training material. The page looks correct because it is a copy. The padlock is there because the connection genuinely is encrypted. The layout, the logo, and the wording are all right. The address bar reads:

blob:https://signin.example-portal.com/6b41f0a2-9d3c-4e77-a1b8-5f2c0e9d7a34

No legitimate sign-in page starts with blob:. Not Microsoft, not Google, not an internal portal. There is no judgment call and no comparison against a remembered domain. Either the target looked at the address bar before typing a password or they did not, and the campaign result tells you which.

That is a rare thing to be able to measure. Most awareness metrics are a proxy for attention. This one is close to a direct reading of it.

Everyone Who Saw It Gets Taught It

Switching the behavior on does more than change how the page is delivered. Every recipient of that campaign gets a training slide built around this specific technique, and only those recipients get it. The slide is conditional on the behavior actually being enabled when their message went out, not on whether it happens to be switched on when they open their training weeks later, so a configuration change after the fact cannot rewrite what a past engagement taught.

It leads with the cue rather than the theory. The recipient sees their own campaign's address the way a normal sign-in page reads, next to the blob: form they actually landed on, with the difference marked. Then it tells them what happened to them specifically: whether they opened the page, and whether they entered credentials. Someone who never clicked gets an explanation rather than an accusation. Someone who submitted credentials sees exactly where.

That is what turns a technique demonstration into an awareness outcome. Learning that your gateway missed something is useful to a security team. Having your people recognise a blob: address bar on sight is the thing that shows up in next quarter's numbers.

What Defenders Should Take Away

  • Detection has to render, not just fetch. Controls that follow a link and evaluate the response have nothing to evaluate here. Controls that execute the page and inspect the result still work. Worth knowing which one you have.
  • Blocklisting has a gap by design. There is no durable address for the credential page, so the reactive path of catching one victim and protecting the next does not apply. Detection has to happen at the moment of use.
  • The browser is where the evidence is. The decisive artifact only ever exists on the endpoint, which argues for weighting browser-layer and endpoint controls rather than treating gateway link inspection as the line of defense.
  • Teach the address bar, not the domain. Most training teaches people to compare a domain against one they half remember. "A sign-in page starting with blob: is never real" is a rule with no ambiguity in it.
  • Phishing-resistant authentication still ends it. Barracuda's own guidance puts FIDO2 and passkeys on the list, and the reasoning holds regardless of how the page was delivered. A credential typed into a page that has no address is still a credential. A passkey bound to the real origin is not.
  • Find out rather than assume. Whether your filters render pages, and whether your people check the address bar, are both answerable by running the technique against your own environment under an authorized engagement.

PhishU's View

Techniques like this succeed because a defensive assumption quietly stopped being true. Fetching a URL and inspecting the response was a good model when phishing pages sat on servers. No amount of tuning fixes a pipeline whose first step finds nothing.

The useful response is measurement rather than alarm. Run the current shape of the attack against your own controls and your own people, see which parts hold, and train against what you find. That is what the Framework is for, and it is why a technique's limits belong in the writeup alongside its strengths.
